# Storage Layer

## Purpose
Provides the unified Database Abstraction Layer (DAL) supporting pluggable backends (SQLite zero-CGO default and PostgreSQL enterprise) with automated dialect-aware migrations.

## Ownership
Owns data models, store interfaces (`UserStore`, `SessionStore`, `AuditStore`, `SettingsStore`, `TargetStore`, `LogStore`, `SourceStore`), dialect translations, and schema migrations. `audit.go` owns the audit hash chain.

## Local Contracts
- `ApplyInstaller` creates missing configuration and issuer/subject-owned administrator/viewer accounts atomically with one keyed audit-chain event; check/resume adds no rows. Foreign names/subjects, different setup ownership, inactive identities and role drift refuse without reactivation or credential changes. Configuration records retain only target-held file references.
- `ApplyInstallerDirectory` changes only an installer-owned identity's status, fenced by `installer.directory.<user id>` (revision + body digest: older or same-revision-different-body refuses, same is a no-op). Unavailable deletes its sessions and MFA challenges in the same transaction with one audit row; it never changes a role.
- Monitoring enrollment shares that transaction and audit. Deterministic setup/key UUIDs
  and `installer.target.*`/`installer.source.*` definitions prove ownership. Refuse foreign
  names/token hashes, changed definitions, revoked sources and missing or drifted owned
  objects; never regrant or repair them implicitly. Store only native token hashes and
  protected file references. Apply locks `log_usage` before target/source access; check is
  read-only. Resume preserves health, silence, source receipt sequence and log/activity rows.
  Omitted targets/sources remain installed. Reports use `configuration` objects named
  `monitoring.target.<key>` and `monitoring.source.<key>` with native IDs.
- `targets.track_json` and `targets.last_result` are JSON owned by `internal/monitor` (`alerts.Track`, `poller.Result`); the store stores and returns them verbatim. `state`, `state_since` and `cause` are denormalised from the track for listing. Silences live in `silenced_until`/`until_fixed`, not in the track JSON, so an admin's silence and a poll never write the same value. Deleting a target cascades its events. `UpdateTarget` with a changed URL resets track, last result/poll/latency, state (`pending`) and cause; silence stays. `ClearUntilFixed` clears only an until-fixed silence with no timed one. `ListEvents` pages by id (`beforeID` exclusive, newest first) with no `COUNT`; `PruneEvents` deletes events older than a cutoff except pending offboarding alerts (`cmd/server` keeps 90 days).
- `migrations.Run` runs on one pinned connection; on Postgres it holds `pg_advisory_lock` for the whole run, so replicas starting together migrate one at a time and each re-reads what is applied. SQLite takes no lock.
- `CompletePasswordChange` atomically compares the old password, updates a flagged local account, clears the flag, deletes sessions/MFA challenges and records `auth.password_changed`. Session/MFA issuance locks the same user row against the verified hash; MFA challenges persist the creation-time password hash, and consumption returns that snapshot to reject stale completions. Migration 4 discards preexisting challenges because their credential snapshot is unknown.
- `ResetAdminPassword` reactivates a local administrator with the replacement flag set and shares the atomic grant purge and audit path with `CompletePasswordChange`; it also works for disabled accounts.
- Audit rows are links of a keyed hash chain (`internal/store/audit.go`, `ky-primitives/auditchain`), keyed by `config.DatabaseConfig.AuditKey`. `server_settings["audit_anchor"]` holds the chain's count and head outside the log but in the same database: it catches an altered or reordered record and a deleted record while the anchor is intact, not someone who rewrites both. `store.Open` refuses to start (`ErrAuditUnplaceable`) whenever the log and its anchor disagree on count or on the tail, or the key does not verify the tail. A log with no digests and no anchor is keyed only in the open whose `migrations.Run` applied migration 6 (`Run` returns the versions it applied); at any later open it is refused as a stripped chain. `AuditStore.Placement()` reports how open found the chain (`new`, `legacy_keyed`, `resumed`, with count and head); `cmd/server` logs it as `audit_chain_placed`, the operator's copy of the anchor outside the database. `place` reads anchor, counts and `MAX(seq)` in one statement (refusing unless total, max and anchor count agree) and the tail by the anchor's sequence. Every append compares the stored anchor with its in-memory chain on the caller's tx and re-reads the tail on a mismatch or a missing anchor, so two processes on one database chain onto each other and a deleted anchor fails the next append (`ErrAuditUnplaceable`) instead of being re-created; before that read every append serialises with other processes on its tx (Postgres `pg_advisory_xact_lock(auditLockKey)`; SQLite a no-op `UPDATE` that takes the write lock under `busy_timeout`), and `LogAudit` retries once from a fresh tail on `isSeqConflict` (duplicate `seq` or SQLITE_BUSY); every append after that chains at write time inside the caller's transaction — `revokePasswordGrants` writes `auth.password_changed` through `auditStore.append` on the same tx that revokes sessions. `append` returns a `finish(committed bool)` closure; the caller must call it exactly once with the transaction's commit outcome, which releases the chain lock and, on a failed commit, drops the in-memory chain so the next append re-reads the tail from disk. Fields hashed, in order: `created_at` (RFC3339Nano UTC, microsecond-truncated), `user_id`, `action`, `resource`, `details`, `ip_address`. `LogAudit` runs on a context detached from the caller with a 10s budget. `AuditStore.VerifyChain` walks the whole log against the anchor without writing; it reads anchor, unkeyed count and `MAX(seq)` in one statement and refuses any record past the anchor. `Ready` takes no lock and no transaction (place's snapshot is one statement), so it cannot deadlock against a concurrent append; it is what `/healthz` asks.
- Collected log lines and imported activity share a byte budget through `log_usage`. `Logs().Append`, `AppendImported`, `Prune`, target deletion, and source writes lock that row first, then source/target rows; this order prevents source claims and revocation from inverting target deletion's lock order. Append checks the source is active in its write transaction and replaces incoming source name and target ID with stored attribution. Empty source IDs are reserved for internal collection. Revocation retains source rows for historical attribution. `received_at` controls age and size eviction; row `bytes` includes all UTF-8 payload lengths, including `target_id`, plus a fixed allowance for row IDs, timestamps and flags. Target deletion subtracts its ID length from matching rows and usage before the foreign key clears the ID. Imported activity is separate from the keyed audit chain.
- Migration 9 adds `log_cursors(key,value)`. `AppendImported` checks the prior cursor under the same `log_usage` transaction lock used for rows, usage and pruning; mismatches return `ErrCursorConflict` without appending. Cursor keys contain pairing generation and stream identity, never credentials/URL. Cursors survive restarts but are removed from recovery snapshots.
- Migration 8 stores only pairing-code and source-token SHA-256 hashes. A code expires at its deadline; `Claim` reads the clock after acquiring `log_usage`, then deletes a valid code with `DELETE ... RETURNING` in the same transaction that inserts the source, so lock contention cannot extend its validity. Exactly one concurrent claim wins and a failed insert rolls back consumption. Source names are 1–64 ASCII letters/digits/underscore/dot/hyphen, beginning with an alphanumeric character.
- `store.Open(ctx, cfg)` initializes and auto-migrates the configured database backend.
- SQLite runs in WAL mode with foreign keys enabled.
- PostgreSQL queries are rebound dynamically from standard positional parameters.
- MFA challenges are consumed with database state transitions that permit exactly one successful use.
- Recovery-code hash updates use optimistic concurrency so simultaneous redemption cannot reuse a code.
- TOTP state moves only by compare-and-swap, and only for `sso_provider = 'local'` on writes that set a secret: `SetTOTPSecret` replaces the pending ciphertext only while `totp_enabled` is false and the old ciphertext matches, so it can never overwrite an enabled secret; `EnableTOTP` requires that exact pending ciphertext; `DisableTOTP` requires `totp_enabled` and clears secret and recovery codes; both also require the caller's checked `password_hash` and an active account, and `totpTransition` returns `ErrNotFound` if the kept session no longer exists. `CreateSession` takes `Credentials` (password hash, `totp_enabled`, and the secret when enabled) and goes through `withCredentials`, so a session is only granted for the TOTP state its sign-in checked. `ResetAdminPassword` clears TOTP too. `totpTransition` runs enable/disable in one transaction that also deletes every other session (by kept token hash) and every MFA challenge and chains `auth.mfa_enabled`/`auth.mfa_disabled` through `audit.append`. Mismatches return `ErrAlreadyExists`. `UpdateUser` still writes the TOTP columns wholesale; only KySignOn sync calls it, for SSO accounts.
- Users carry `RoleAdmin` or `RoleViewer`; `CreateUser` and `UpdateUser` return `ErrInvalidRole` for anything else. New users default to viewer.


- `Logs().ActivityBursts` computes rolling event-time windows in SQL for separate
  `(app,actor)` and `(app,IP)` groups, excluding empty identities. It uses the supplied pure
  policy and the timeline's target/app/actor/outcome/time filters, ignores pagination,
  and returns the newest qualifying window per group, newest first, at most 100 groups.
  SQLite converts seconds and fractional seconds separately to integral microseconds to
  avoid Julian-day floating-point errors at the inclusive boundary; PostgreSQL uses epoch
  microseconds. No retained-row collection is materialized in Go.

- Migration 10 keeps one `ingest_seq`/`ingest_digest` receipt per paired source. `AppendSequenced` checks active source ownership under the existing `log_usage` transaction lock and commits the next receipt, logs, activity, usage and pruning together. Exact latest replay makes no writes, even after retention deletes its payload; conflicts and failed inserts leave the receipt unchanged. Internal imports and unsequenced sources retain their existing behavior. These receipts are acknowledgment state, separate from the keyed audit chain.
- Migration 11 adds an administrator-selected `offboarding_alerts` pairing/source grant,
  default off. It requires a watched target and is copied from the consumed code, never the
  claimant's JSON. Granted sources require sequenced single-log/single-activity kyoffboard
  projections. Failed outcomes insert one `offboarding_failed` target event with pending
  notification in the same transaction as the receipt and payload; replay adds nothing.
  Target deletion removes the events and alert scope; subsequent writes refuse rather than
  silently omit alerts. Health tracks are unchanged. `NextOffboardingAlert` reads the oldest
  pending event through a partial index; the monitor owns delivery and terminal reasons.
- Migration 12 adds `sessions.sso_sid`, `sso_logouts` (by `sid`) and `sso_subject_logouts` (by provider and subject, with a `cutoff`; it never moves back). In the same step it deletes every session of a non-`local` user, all of which predate `sso_sid` and so no logout could reach; local password sessions stay. It runs once, so a later start never signs out SSO sessions issued afterwards, with or without a `sid` (`TestMigration12DropsUnreachableSSOSessions`, SQLite and Postgres). `EndSSOSession` and `EndSSOSubject` commit their fence before deleting sessions, and `CreateSession` checks both fences only after its insert commits, so under read committed a logout racing a login always ends it; a fenced create deletes its row and returns `ErrSSOSessionEnded`. The subject fence matches sessions by `created_at`, so it relies on SSO sessions being dated by the ID token's `iat`. Expired fences are pruned on the next call that writes one. Capsules carry all three; a restored fence only refuses a login KySignOn already ended. `TestEndSSOSessionFencesTheSID` pins the `sid` fence, the own-row delete and fence expiry; `TestEndSSOSubjectFencesTheSubject` pins the cutoff delete, the subject fence and that it never moves back.
